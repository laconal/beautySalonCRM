## Бизнес-процессы и правила (важно)

Ниже собраны ключевые бизнес-правила, вынесенные из логики сервисов — используйте их при разработке фронтенда, валидации и UX-решениях.

- Appointment (посещение)
  - При создании проверяются пересечения по клиенту и по сотруднику; если время занято — возвращается 409.
  - При создании проверяется, что сотрудник активен, не архивирован и работает в указанный промежуток времени.
  - Нельзя прикреплять к посещению архивированные услуги/товары — будет 409.
  - При попытке отменить посещение (`PATCH /{id}/cancel`):
    - требуется указать причину отмены `client changed his mind (клиент передумал)`, `mistaken input (ошибочный ввод)`, `incorrect client (некорректно выбранный клиент)`, `incorrect date (некорректная дата)`
    - если посещение уже отменено — 400;
    - если посещение помечено как оплаченное (`paid == True`) — отмена запрещена, сначала нужно отменить связанный чек (receipt) — 400.

- AppointmentRecords (записи внутри посещения)
  - Нельзя создавать/обновлять/удалять запись, если для посещения есть активный чек (receipt) в статусе `PENDING` или `PAID` — сервисы требуют сначала отменить чек (400).
  - При добавлении записи проверяется активность сотрудника, наличие сервисов/товаров, доступность на складе и причины изменения цены при отличии от стандартной цены.

- AppointmentServices (услуги/товары в записи)
  - Создание/обновление/удаление услуги из посещения аналогично: запрещено при наличии активного чека для посещения (400).
  - Запись об оказанной услуге может содержать либо `service_id`, либо `material_id`, но не одновременно — в противном случае 400.
  - При изменении цены требуется обоснование (`price_changed_reason`) — иначе 400.

- Receipts / Payments (чеки и оплаты)
  - Нельзя создать новый чек для посещения, если уже существует активный чек (PENDING/PAID). Попытка выдаст 400 с пояснением.
  - Оплата (`POST /api/v1/payments`) проверяет, что чек не оплачен полностью; при попытке доплатить полностью оплаченный чек — 400.
  - Метод оплаты `DEPOSIT` уменьшает депозит клиента; при недостаточном депозите операция запрещена (400).
  - При переплате создаются автоматические транзакции и (опционально) перевод переплаты в депозит, если клиент отметил `add_change_to_deposit`.
  - При успешной полной оплате для чеков типа `APPOINTMENT` генерируются `Payroll` записи (комиссии сотрудникам) — эти payrolls помечаются как автоматически сгенерированные.
  - Отмена чека (`POST /api/v1/receipts/cancel`) выполняет: возврат депозита (если платили депозитом), отмену связанных платежей, пометку payrolls как CANCELLED, возврат использованных материалов на склад (для direct sale), снятие флага `appointment.paid`, отмену связанных транзакций.

- Transactions (транзакции)
  - Транзакции автоматически создаются при оплате и при других операциях (auto_generated = True).
  - Автогенерируемые транзакции нельзя отменять вручную — при попытке cancel возвращается 400 и подсказка отменить связанные счета/чек.

- Payrolls (выплаты / комиссии)
  - Payrolls, созданные автоматически (например, через оплату чека), помечаются `auto_generated` и не подлежат редактированию или удалению: сервисы блокируют такие операции (400/409).
  - Нельзя изменить/удалить запись payroll, если она связана с `payout_id` (выплата уже проведена) — сначала нужно отменить выплату.
  - Отмена payroll требует, чтобы запись не была автоматически сгенерирована; также нельзя отменять заархивированные записи.

- Payouts (выплаты сотрудникам)
  - При создании выплаты можно передать явный список `payrolls` или сформировать их по периоду (start_date/end_date) или для всех ожидающих.
  - Сервис выполняет проверки по `payrolls`: они должны существовать и принадлежать указанному сотруднику; также сервис проверяет их статусы перед включением в выплату.
  - После успешной выплаты статус включённых `payrolls` меняется на `PAID`, создаётся транзакция расхода и привязывается `payout_id`.
  - Отмена выплаты помечает транзакцию(и) как отменённые и переводит `payrolls` обратно в статус `PENDING` (и снимает `payout_id`).
  - При отмене выплаты также запрещено изменять уже заархивированные или ранее отменённые выплаты.

- Clients (клиенты)
  - Параметр `deposit` не может стать отрицательным; операции пополнения/списания реализованы через `updateDeposit` с явной операцией `1` или `-1`.
  - При обновлении депозита проверяется существование клиента и корректность операции; при ошибках возвращается 400/404.
  - Получение списка посещений клиента (`GET /clients/{id}/appointments`) возвращает пагинированный результат.

- Employees (сотрудники)
  - При создании/обновлении можно привязать `services` по `id`; все указанные услуги должны существовать.
  - Нельзя привязать архивированную услугу или использовать архивированную специализацию — сервисы вернут 409.
  - Endpoints для рабочего графика и payrolls доступны и возвращают пагинированные списки.

- Materials (товары / запасы)
  - Поля `article` и `name` не могут быть пустыми при обновлении — иначе 400.
  - Операции изменения количества (`update-quantity`) принимают операцию `1` или `-1` и не позволяют получить отрицательный остаток.
  - При создании чека direct-sale количество списывается со склада; при отмене чека использованные материалы возвращаются на склад.

- Services (услуги) и Service Categories
  - При привязке услуги к категории проверяется существование категории и её статус (`archived`); привязка к архивированной категории запрещена (409).
  - При архивировании услуги удаляются связи с сотрудниками (чтобы сотрудники не предлагали архивированные услуги).
  - Импорт услуг из Excel требует колонок `service_category`, `service`, `price`.

- Specializations
  - Простая CRUD-логика: создание, обновление, удаление через репозитории; при отсутствии сущности возвращается 404.

- Notifications
  - Создание уведомления сохраняет запись; есть отдельные методы `archive` и `delete`.
  - Метод `deliver` пытается отправить через SSE и помечает `delivered_at` при успешной доставке.
  - SSE поток: `/notifications/stream` — подписка на канал текущего staff (требуется авторизация).

- Staff
  - При создании пользователя (`Staff`) проверяется уникальность `login` и (опционально) существование связанного `employee`.
  - Пароли хэшируются сервером; валидация и ошибки 409/404 возвращаются при конфликтах или отсутствии сущности.

- Work schedules
  - Создание расписания требует существования сотрудника; ошибки 404 возвращаются при отсутствии.
  - Удаление/обновление расписания возвращает 404, если запись не найдена.

- Absences (отсутствия)
  - CRUD для отгулов: при создании проверяется сотрудник; стандартные 404/400 при ошибках.

- Tenant Branches (филиалы)
  - Управлять филиалами может только головная организация (`parent_id == null` у самого tenant'а) — иначе 403 `ONLY_FOR_PARENT_TENANT`. У филиала не может быть своих филиалов (иерархия из двух уровней).
  - Данные филиалов не доступны головной организации напрямую (списками) — только через агрегированные отчёты (`/report`, `/report/{id}`), которые считают количество сотрудников/сотрудников-исполнителей/клиентов/записей/услуг/товаров и суммы доходов/расходов по неархивированным и неотменённым записям.
  - При создании/управлении админом филиала проверяется, что `admin_id` реально принадлежит указанному `branch_id` (409 `STAFF_TENANT_CONFLICT`), а логин уникален глобально по всей системе, не в рамках организации (409 `STAFF_LOGIN_DUPLICATE`).
  - При переименовании филиала (`PATCH /update`) проверяется, что новое `name` не занято другой организацией (409 `TENANT_NAME_TAKEN`).
  - Деактивация филиала или его админа (`active = false`) вступает в силу немедленно — у уже авторизованных сотрудников этого филиала следующий же запрос будет отклонён, без ожидания истечения токена.

---

Примечание: большинство сервисов используют одинаковые шаблоны ошибок: `404` для "not found", `400` для валидации/логических ограничений и `409` для конфликтов (например, использование архивированных объектов или дубликаты). Рекомендуется в UI показывать `detail` из ответа при 4xx для информирования пользователя.

Применяйте эти правила в UI/UX: блокируйте кнопки отмены, показывайте подсказки (почему операция недоступна), и до выполнения действий запрашивайте подтверждение у пользователя.
